严重问题（直接威胁 G3 / G6）
S1. conversation_id 是否在 sessionStart 可得 —— canonical 绑定的根基未验证
§6.2 把 conversation_id 定为 canonical，且"bind 后不可变"，并禁止 beforeSubmitPrompt 用 payload 覆盖已绑定 id（§6.2、§6.2.5 重绑定规则）。 问题：binding 在 session.start 时刻建立（§6.2 时机 1）。如果 Cursor 的 sessionStart payload 不暴露 conversationId、而只有 beforeSubmitPrompt 才有，那么：

sessionStart 只能走优先级 3 生成 sess_*_{nano} 或拒绝；
之后真正的 conversation_id 出现时，因"不可变 + 不自动改绑"只会写 binding_mismatch.log，canonical 永远立不住。
文档把 conversation_id 当作既定可得，但没有列出"各 Cursor hook 实际提供哪些 id 字段"的对照。这是 G3 成败的前提，必须先核实再定优先级。

S2. task_id 与 EnsureSessionReady 自动 bootstrap 的时序冲突
§6.2 规定 task_id 一旦"写入 binding 后全线程不变"，且首选来源是"首次 beforeSubmitPrompt 见到 prompt 时的指纹"，兜底是 task_{agent_type}_auto。
§6.2.1 规定乱序事件（如先来 afterFileEdit、还没 sessionStart/prompt）会自动合成 session.start 并补 DB session。
矛盾点：写一条 DB session 行需要 task_id。若自动 bootstrap 发生在任何 prompt 之前，只能用兜底 task_{agent_type}_auto 并（按"binding 不可变"）固化；等真正的 beforeSubmitPrompt 算出 prompt 指纹时，因 task_id 已不可变而无法回填，task 永久停留在 auto。 文档没有说明：自动 bootstrap 是否写 binding 的 task_id？若写则与"首次 prompt 指纹"冲突；若不写，则 DB session 的 task 与后续 binding task 不一致。这一点 §6.2.1 只说"不覆盖 session_id……仅补齐 DB session 行"，对 task_id 的处理是空白。

S3. ingest 幂等缺少持久化账本
§9.2 声明幂等：同一 ingest_id 重试时已处理条目标记 deduped，"ingest 层记录 (ingest_id, event_index)"。 但 §6.1 的运行时状态文件清单里没有任何文件承载这个 (ingest_id, event_index) 账本（ingest.jsonl 是审计追加日志、dead_letter.jsonl 是失败队列，都不是幂等索引）。 没有落盘的去重账本，"同一 ingest_id 重试幂等"无法实现 —— 这是 G6 的核心承诺之一，属逻辑缺失。

S4. 条级对账信息不完整（dead_letter 缺 event_index）
§9.2 的幂等/失败语义以 (ingest_id, event_index) 为粒度，但 §9.3 可观测性里 dead_letter.jsonl 只说"补充 ingest_id 字段"，未提 event_index。批量 best-effort 逐条失败时，仅凭 ingest_id 无法定位是第几条失败 → 条级对账/重放无法精确，G6 打折。

中等问题（设计自洽性 / 兜底有效性）
M1. 跨 kind 兜底去重的 fingerprint 字段不对齐（§5.4 + §5.2）
§5.4 兜底策略 3：legacy 双写时，对 turn.completed 内与 atomic-dedup 相同 fingerprint 的项跳过。 但 §5.2 的 file.edit.summary fingerprint 需要 after_hash（无则取 content_summary 前 200 字）。turn.completed 里的 file_edits[]（TurnPayload 形状）未必携带 after_hash，两条通道极可能算出不同 fingerprint → 兜底去重形同虚设，只能靠 DB 层 content_hash。 要么强制两侧 fingerprint 输入字段一致，要么明确"接入层兜底对 file.edit 不保证、完全依赖 DB"。当前表述给了一种实则不可靠的中间承诺。

M2. Cursor afterAgentResponse 的 turn_id 来源未定义（影响 §7.2 回合隔离）
§7.2 要求 inject-cache 按 turn_id 隔离：beforeSubmitPrompt 写入带 turn_id，afterAgentResponse 读取时"仅当 turn_id 一致才合并 trace"。同理 §5.2 turn 去重键含 turn_id。 但文档没说明 afterAgentResponse 这一侧从哪里取得与 beforeSubmit 相同的 turn_id。若 turn_id = prompt 指纹，afterAgentResponse 未必拿得到原始 prompt 文本来重算；若靠读 prompt-cache.json，应明写。否则回合匹配会落空，retrieval_trace 串轮/丢失。这是 G4 闭环的一个空白。

M3. 自动 bootstrap 与真实 session.start 在乱序/同批下可能重复建 session / 触发 mismatch
§6.2.1 的 bootstrap 用 SessionBinder.Resolve 得到 session_id。但若该 session_id 是在无 conversation_id 时生成的合成值，随后到来的真实 session.start（带 conversation_id）会与已绑定值不同 → 按 §6.2 走 binding_mismatch.log 不改绑。结果：会话链以合成 id 固化，真实 canonical 反而被拒。这与 S1/S2 同源，建议合并定义"bootstrap 产生的 binding 是否允许被首条真实 session.start 升级/改绑"。

轻微问题（表述/一致性）
L1. §4.4 缺省 kind 推断"步骤 3"位置错乱
推断列表是针对单个对象的优先级，却把"若存在批量 events[] → 不推断，逐条执行步骤 1–6"放进步骤 3。批量/单条的根判别在 §9.2 已经先行完成（含 events[] → BatchEnvelope），到 kind 推断时面对的必然是单条 item。步骤 3 属冗余且让读者误以为 kind 推断要自己判断批量。建议删除或移到 §9.2 根判别处。

L2. §4.4 步骤 4"剥离数组字段 或 拒绝并 dead-letter"二义
对"原子事件枚举却误带 Turn 数组字段"给了两种相反处理（自动剥离 vs 拒绝）。需定一个默认行为，否则不同实现/不同 Driver 行为不一致，且影响对账统计。

L3. ExpandMode=v2"必须显式 kind"与"默认 legacy"的张力
§4.4 v1 兼容说明要求 v2 下 Driver 必须显式 kind=capture.atomic，但 §10.5/§12 默认 legacy。这意味着 G2（事件粒度正确）在默认配置下并不成立，只有切到 v2 才达成。这是可接受的分阶段策略，但文档在"目标"处宜显式标注"G2 在 P2/v2 后达成"，避免读者误以为默认即满足。

L4. producer 含 mcp: 拒绝规则与 afterMCPExecution 的边界值得加一句
§3.3.1/§9.2 对 producer 以 mcp: 开头者拒绝（WRONG_TRANSPORT），而 Cursor afterMCPExecution 走 ingest 用 cursor_hook:afterMCPExecution——二者不冲突（一个是 hook 捕获 MCP 工具结果，一个是 MCP 直连），但容易被误读。建议补一句"hook 捕获到的 MCP 工具结果属 *_hook: 通道，不受 mcp: 拒绝约束；同时应过滤 theone 自身 MCP 工具避免自捕获"（后者在记忆规则里有，但本设计文档未提，属一致性补充）。

建议（按优先级）
先做外部事实核查（S1）：列一张"Cursor 各 hook 实际提供的会话/回合 id 字段"对照表，再据此定 conversation_id 优先级与绑定时机。这是 G3 的前置条件。
在 §6.2/§6.2.1 之间补一节**"bootstrap 与首条真实 session.start 的关系"**，明确 task_id 是否随 bootstrap 固化、合成 binding 是否允许被 canonical 升级（S2、M3）。
在 §6.1 状态文件表增加幂等账本文件（如 ingest-ledger.json，存 (ingest_id, event_index) 集合/LRU），并在 §9.3 给 dead_letter.jsonl 补 event_index（S3、S4）。
统一跨 kind fingerprint 的输入字段，或明确"file.edit 兜底仅靠 DB"（M1）；明确 afterAgentResponse 的 turn_id 取自 prompt-cache.json（M2）。
修订 §4.4 推断步骤（删步骤 3、定步骤 4 默认行为），并在目标表标注 G2 的达成阶段（L1–L3）。
