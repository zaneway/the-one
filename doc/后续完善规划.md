## F-002：语义信号词规则可配置化（数据库 / 配置文件）

**状态**：待规划  
**关联模块**：`internal/processor`、`internal/config`、`internal/storage/sqlite`（若落库）  
**关联配置**：建议新增 `processor.signal_rules` 或独立表 `processor_signal_rule`  
**与 F-001 关系**：F-002 解决「词表写死在代码里」；F-001 解决「仅靠词表无法判断语义」。优先实现 F-002 成本更低、无外部依赖。

### 现状与原因

`rule_based` 通过 `hasAnySignal` 做子串匹配（大小写不敏感）。其中 `hasSemanticSignal` 专用于 `conversation.message`（及部分对话类路径），词表**硬编码**在源码中：

```go
// internal/processor/rule_based.go
func hasSemanticSignal(text string) bool {
	return hasAnySignal(text, "记住", "了解","理解","掌握","学习","分析","以后", "必须", "不要", "不能", "需求", "验收", "假设", "待确认", "约束", "复查", "prefer", "requirement", "assumption", "open issue", "constraint", "review")
}
```

同类硬编码还分布在同一文件（建议一并纳入可配置范围，避免只改一处）：

| 规则集（建议命名） | 用途 | 当前触发位置（示意） |
|--------------------|------|----------------------|
| `conversation_semantic` | 对话消息是否抽证据 | `hasSemanticSignal` → `EventConversationMessage` |
| `agent_response_high_signal` | 智能体响应摘要 | `EventAgentResponseSummary` |
| `file_edit_high_signal` | 文件编辑摘要 | `EventFileEditSummary` |
| `declaration_classify_*` | 声明类候选分类 | `classifyDeclaration` 各分支 |
| `tool_failure` / `design_review` 等 | 工具失败、设计复查识别 | `isFailedToolEvent`、`isDesignReview` 等 |

现状问题：

1. 增删关键词必须改代码、发版，无法按项目或团队微调。  
2. Cursor 摘要常用中性表述（如「用户询问…」），与默认词表不匹配，自动化晋升率低。  
3. 中英文词表混在 Go 常量中，不利于运营侧维护与审计。  
4. 与 F-001 不同，本条**不依赖大模型**，适合作为 v1.x 内的小步增强。

### 目标

1. **外置规则**：将 `hasSemanticSignal` 及同类 `hasAnySignal` 词表迁出源码，支持运行时加载。  
2. **双层来源**（建议）：  
   - **配置文件**（`theone.yaml`）：全局默认、部署即生效、适合单机与个人场景；  
   - **数据库**：按 `workspace_id` / `project_id` 覆盖或追加，适合多项目、团队统一维护。  
3. **按事件类型绑定**：规则集与 `event_type`（及可选 `memory_type` 分类阶段）映射，保持与现有分支逻辑一致。  
4. **热更新或重启加载**：至少支持修改配置后重启 `serve` 生效；数据库方案可选缓存 TTL 或版本号刷新。  
5. **默认回退**：未配置时使用与当前代码等价的内置默认词表，保证升级兼容。

### 与现有架构的接点

| 现有能力 | 扩展方式（建议） |
|----------|------------------|
| `hasAnySignal` / `hasSemanticSignal` | 改为从 `SignalRuleRegistry` 读取词表 |
| `config.ProcessorConfig` | 增加 `signal_rules_path` 或内联 `signal_rules` 块 |
| SQLite migration | 可选表：`processor_signal_rule`（scope、event_type、rule_set、keywords_json、enabled、priority） |
| `RuleBasedProvider` | 构造时注入 `SignalRuleRegistry`；单测用内存规则 |
| 诊断 MCP | 可选 `memory.processor.rules` 列出当前生效词表（脱敏、只读） |

匹配语义建议保持：**子串包含、忽略大小写**（与现实现一致），避免静默改变行为；若未来支持正则，需单独规则类型字段。

### 建议设计方向（草案）

#### 1. 规则模型（示意）

```yaml
# theone.yaml 片段（示意）
processor:
  provider: rule_based
  signal_rules:
    conversation_semantic:
      event_types: [conversation.message]
      keywords: ["记住", "必须", "需求", "约束", "复查"]
    agent_response_high_signal:
      event_types: [agent.response.summary]
      keywords: ["结论", "决策", "约束", "假设"]
```

数据库表（若采用）可增加字段：`scope`（`global` / `workspace` / `project`）、`override_mode`（`replace` / `merge`）、`updated_at`，合并时 **project > workspace > global > 内置默认**。

#### 2. 加载顺序（建议）

```text
内置默认词表（与当前 rule_based.go 一致）
  → theone.yaml 全局覆盖/合并
  → 数据库按 workspace_id / project_id 合并
  → 注入 RuleBasedProvider
```

#### 3. 与 F-001 的配合

| 场景 | 行为 |
|------|------|
| 仅 F-002 | 调词表即可让更多摘要通过 `conversation.message` 过滤 |
| F-002 + F-001 hybrid | 词表命中则直接抽证据；未命中再走大模型 |
| 仅 F-001 | 词表仍可保留为最便宜的 first-pass |

#### 4. 治理与安全

- 单条规则关键词数量上限（如 ≤100），单词长度上限，防止配置膨胀。  
- 禁止在词表中配置完整句子级「绕过最小化」内容；仍受 `capture` / `memory` 长度校验约束。  
- 变更可写审计日志（谁、何时、改了哪套规则集）。

### 验收标准（草案）

- [ ] `hasSemanticSignal` 不再依赖硬编码切片；修改 `theone.yaml` 后重启即可让新词生效。  
- [ ] （若做数据库）指定 `project_id` 的追加词表仅作用于该项目下事件的抽取。  
- [ ] 未配置任何自定义规则时，行为与当前版本一致（含 `TestRuleBasedInsufficientInputReturnsEmpty`）。  
- [ ] 文档列出全部规则集名称、对应 `event_type`、配置示例。  
- [ ] 无效配置（空词表、未知 `event_type`）启动时报错或告警，不静默禁用过滤。

### 风险与依赖

| 风险 | 缓解思路 |
|------|----------|
| 词表过宽导致记忆噪声 | 仍走准入与 `pending_review`；提供推荐词表模板 |
| 多源合并歧义 | 明确优先级与 `merge`/`replace` 语义；单测覆盖 |
| 与 F-001 重复建设 | F-002 只做词表外置；语义理解留给 F-001 |

- 代码：`internal/processor/rule_based.go`（`hasSemanticSignal`、`hasAnySignal`、`classifyDeclaration`）

## F-001：基于大模型的记忆价值分析（多厂商抽象）

**状态**：待规划  
**关联模块**：`internal/processor`、`internal/automation`、`internal/config`  
**关联配置**：`processor.provider`（仅 `rule_based`）、`processor.max_related_events`、`processor.max_candidates_per_event`

### 现状与原因

当前默认抽取器为 `rule_based`（`processor.provider: rule_based`）。其对 `conversation.message` 的处理策略为：

- 从 `content_summary` 等字段拼出待检文本；
- 调用 `hasSemanticSignal`，仅当包含「记住、必须、需求、约束」等**固定信号词**时才生成证据；
- 否则 `ExtractEvidence` 返回空列表。

相关代码：

- `internal/processor/rule_based.go`：`ExtractEvidence` 中 `capture.EventConversationMessage` 分支；
- `hasSemanticSignal`：关键词白名单匹配。

因此出现下列**符合设计、但易误解**的现象：

1. Cursor 等场景下，全局规则要求每条用户消息调用 `memory.observe`，事件会写入 **`raw_event`（事实层）**。
2. 异步任务 `extract_evidence` 仍会执行且通常**成功**，但 `evidence_count` 为 0。
3. 不会入队 `generate_memory_candidate`、`compute_admission`，**不会**写入 **`memory_item`**。
4. 用户侧感受：「observe 一直在记，长期记忆却不增长」。

这与 README 原则一致：**原始对话不等于长期记忆**、**不是所有内容都该被记住**。但在「仅规则、无模型」前提下，中性摘要（如「用户询问如何配置 MCP」）几乎无法通过白名单，自动化晋升率偏低。

单元测试 `TestRuleBasedInsufficientInputReturnsEmpty`（摘要为「继续」）将上述行为固化为预期。

### 目标

1. **记忆价值判断**：由大模型分析最小化后的事件摘要（及可选近邻事件、已有记忆摘要），判断是否具有长期记忆价值，并输出结构化结论（是否抽证据、建议记忆类型、置信度、理由码等）。
2. **多厂商抽象**：抽取层支持多种大模型后端（如 OpenAI 兼容接口、Anthropic、本地 Ollama 等），通过配置切换，不绑定单一供应商。
3. **与现有管道兼容**：仍走「事实层 → 证据 → 候选 → 准入 → 记忆层」；**准入控制器**（`AdmissionController`）仍可在本地执行，避免未审核内容直接变为稳定记忆。
4. **可降级**：保留 `rule_based`；无网络或 `provider: rule_based` 时行为与当前版本一致。

### 与现有架构的接点

| 现有能力 | 扩展方式（建议） |
|----------|------------------|
| `processor.Provider` 接口（`ExtractEvidence` / `GenerateCandidates`） | 新增实现，如 `llm_based`，或 `hybrid`（先规则、再模型） |
| `config.ProcessorConfig.Provider` | 扩展合法取值；增加模型端点、模型名、超时、并发等子配置 |
| `automation.Service` + `JobDispatcher` | 三步 `async_job` 类型不变；仅替换 `provider` 实例 |
| `ingest.CheckMinimizedContent` / `capture.CheckMinimizedObserve` | 模型**输入输出仍受最小化边界约束**，禁止回写全文 |

不建议让大模型绕过 `memory_item` 的准入与 review 流程，亦不建议把模型输出直接当作 system prompt。

**与接入层边界**：F-001 仅在 Go `async_job` / `processor` 内实现；Driver / Hook **不**同步调用 LLM（见 [Agent 接入层与 Hook 设计.md](./Agent%20接入层与%20Hook%20设计.md) §3.4）。

### 建议设计方向（草案）

#### 1. 双接口分层

```text
processor.Provider          # 现有：证据 + 候选（编排）
    └── 内部可调用
memory_analyzer.Analyzer    # 新增：仅负责「是否值得记 + 结构化草图」
    └── 实现
        ├── rule_based（现有逻辑可迁入）
        └── llm（多后端）
```

#### 2. 大模型后端抽象（示意）

```go
// 示意，非最终实现
type LLMBackend interface {
    Name() string
    Complete(ctx context.Context, req CompletionRequest) (CompletionResponse, error)
}
```

- 配置块可参考现有 `embedding` 的 `provider` 模式：`provider` + `base_url` + `model` + `api_key_env`。
- 注册表：`openai_compatible`、`anthropic`、`ollama` 等，统一请求/响应 DTO，便于单测用 mock。

#### 3. 模型输出约束（建议）

模型返回 JSON，例如：

- `worth_remembering`: bool  
- `memory_type`: 与 `memory.Type*` 对齐  
- `scope`: 与 `memory.Scope*` 对齐  
- `interpreted_statement`: 短句，长度受 `max_evidence_chars` 限制  
- `keywords`: 数组，条数受 `max_keyword_count` 限制  
- `confidence`: 0~1  
- `reason_codes`: 供诊断与准入参考  

服务端校验后再写入 `evidence` / `MemoryCandidate`；校验失败则丢弃或降级为 `rule_based`。

#### 4. 运行模式（建议）

| 模式 | 说明 |
|------|------|
| `rule_based` | 当前行为，默认，无外部依赖 |
| `llm` | 对话类事件优先走模型判断 |
| `hybrid` | 规则命中高信号词则跳过模型；否则调用模型 |

#### 5. 可观测性

- `async_job` 的 payload 中记录：`analyzer`、`model`、`worth_remembering`、`reason_codes`、耗时。  
- `memory.automation.status` 或诊断工具可查看模型调用失败率，便于 Cursor 场景排障。

### 验收标准（草案）

- [ ] 配置 `processor.provider: llm`（及有效模型配置）时，中性 `conversation.message` 在模型判定为高价值时可生成证据并进入候选管道。  
- [ ] 配置为 `rule_based` 时，行为与当前版本一致（含「继续」类用例仍为空）。  
- [ ] 至少支持两种后端实现（例如 OpenAI 兼容 + 本地 Ollama），通过配置切换，无需改代码。  
- [ ] 模型输出超长或含禁止字段时被拒绝，不写入超界正文。  
- [ ] 模型不可用（超时、鉴权失败）时：可配置为「丢弃」或「回退 rule_based」，且不阻塞 `observe` 主路径。  
- [ ] 文档说明：事实层与记忆层差异、成本与隐私提示。

### 风险与依赖

| 风险 | 缓解思路 |
|------|----------|
| 延迟与成本 | 异步 job 内调用；批量/去重；hybrid 减少调用次数 |
| 隐私 | 默认本地 `rule_based`；模型仅收摘要；支持本地推理后端 |
| 幻觉记忆 | 准入评分 + `pending_review`；证据必须带 `source_ref` |
| 与「无 embedding 也可运行」原则 | 模型抽取为可选能力，与 `embedding.provider` 独立配置 |
