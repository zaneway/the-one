# 《Inside the Scaffold: A Source-Code Taxonomy of Coding Agent Architectures》学习记录

- 论文地址：https://arxiv.org/html/2604.03515v2
- 作者：Benjamin Rombaut
- 版本：arXiv:2604.03515v2，2026-04-10
- 我的阅读目标：理解“Coding Agent 到底是如何被脚手架代码组织起来的”，并把其中可复用的架构视角沉淀下来。

## 1. 一句话总结

这篇论文最重要的贡献，不是再讲一遍“Agent 会规划、会调用工具、会反思”，而是把 **Coding Agent 的真正差异点** 拉回到源码级脚手架：控制循环怎么写、工具如何暴露、状态如何管理、上下文如何压缩、模型如何路由。论文认为，实际系统并不适合被分成几个离散类别，而更适合被理解为 **多个循环原语在连续谱系上的组合**。

## 2. 论文在解决什么问题

作者认为，现有研究里对 Coding Agent 的分类大多过于抽象：

- 说某个 Agent “会用工具、会规划、会反思”，并不能解释它为什么比另一个 Agent 更稳、更贵或更容易失败。
- 只看运行轨迹可以看到 Agent “做了什么”，但看不到“为什么会这么做”。
- 真正决定行为模式的，其实是模型外面的脚手架代码，包括控制流、工具定义、状态管理和上下文策略。

所以，这篇论文想解决的是：

- 给 Coding Agent 建立一个源码级、可比对、可复用的架构分类框架。
- 让研究者分析性能差异时，不再把“模型能力”和“脚手架设计”混在一起。
- 给工程实践提供一张设计空间地图，帮助构建新 Agent 时少走弯路。

## 3. 研究方法

作者分析了 13 个开源 Coding Agent，在固定 commit 上做源码级比较，并把它们放进一个三层、12 个维度的分类框架中。

### 三层架构视角

#### Layer 1：Control Architecture

关注 Agent 如何决定“下一步做什么”：

- Control Loop Strategies
- Loop Driver
- Control Flow Implementation

#### Layer 2：Tool and Environment Interface

关注 Agent 如何与代码库和执行环境交互：

- Tool Set Design
- Edit and Patch Format
- Tool Discovery Strategy
- Context Retrieval Paradigm
- Execution Isolation

#### Layer 3：Resource Management

关注 Agent 如何管理资源与长期运行能力：

- State Management
- Context Compaction
- Multi-Model Routing
- Persistent Memory

这个框架的价值很大，因为它把“Agent 架构”从抽象概念拆成了可落地的工程问题。

## 4. 论文最核心的发现

## 4.1 Agent 不是离散类型，而是连续谱系

这是全文最重要的观点。

作者认为，Coding Agent 不是几种固定类型，比如“ReAct 型”“Planning 型”“Tree Search 型”，而是分布在不同设计光谱上的系统：

- 控制策略从固定流水线一直到 Monte Carlo Tree Search。
- 工具数量从 0 到 37 不等。
- 上下文压缩策略也不是单一方案，而是至少有 7 种不同做法。

换句话说，真正的系统设计不是“选一个流派”，而是沿着若干维度做权衡与组合。

## 4.2 五类循环原语是搭积木式组合的

论文把 Coding Agent 常见控制逻辑提炼成 5 个循环原语：

- ReAct
- generate-test-repair
- plan-execute
- multi-attempt retry
- tree search

作者特别强调：这些原语不是互斥分类，而是 **可组合的控制积木**。13 个 Agent 里有 11 个都不是只靠单一控制结构，而是把多个原语叠加起来。

这点很有启发：

- 真正强的 Agent 往往不是靠一个“神奇总循环”。
- 更常见的做法是：主循环负责推进任务，局部子流程负责验证、回退、重试或扩展搜索。
- 所以设计 Agent 时，应该优先考虑“循环组合策略”，而不是给系统贴单一标签。

## 4.3 有些维度收敛，有些维度明显分化

论文发现，不同 Agent 在某些方面越来越像，在另一些方面仍高度分化。

### 相对收敛的维度

这些维度容易受外部现实约束影响，所以做法趋同：

- 工具能力类别：读、搜、改、执行，几乎是自治 Coding Agent 的基础能力集合。
- Edit/Patch 格式：因为需要跟代码库和 diff 工具兼容，工程上很难太离谱。
- Execution Isolation：安全与可回滚要求会逼着系统采用更稳妥的边界。

### 明显分化的维度

这些维度仍属于开放设计问题：

- Context Compaction
- State Management
- Multi-Model Routing

这说明目前 Agent 领域真正还在快速演进的，不是“会不会调用工具”，而是：

- 长上下文怎么维持
- 复杂任务状态怎么表达
- 不同模型如何协同分工

## 4.4 工具数不是越多越好

论文中一个很值得注意的观察是：工具数量差异极大，但底层能力类别并没有那么大差异。

也就是说：

- 有的 Agent 提供很多精细化动作类工具。
- 有的 Agent 提供更少、更通用的工具封装。
- 工具接口数量增长，并不自动等价于能力增长。

这背后其实有一个工程权衡：

- 工具太少，模型做事不够可控，动作粒度太粗。
- 工具太多，模型容易混淆，选择成本和 prompt 负担都会增加。

因此，工具设计的关键不是“越全越好”，而是 **能力覆盖、调用清晰度、认知负担** 三者之间的平衡。

## 4.5 上下文压缩不是优化项，而是架构必选项

论文把 Context Compaction 作为一个独立维度看待，这一点非常重要。

这意味着：

- 当任务变长、仓库变大、交互轮次变多时，上下文压缩不是后期补丁。
- 它本身就是 Agent 架构的一部分。
- 如果没有稳定的上下文压缩机制，系统迟早会在 token、稳定性和任务持续性上出问题。

这和很多真实使用体验是一致的：短任务时，很多架构差异不明显；长任务一来，摘要、裁剪、状态外存、事件日志这些能力立刻决定上限。

## 4.6 IDE 耦合本身也是一种架构选择

论文提出一个很有现实感的主题：IDE as Architecture。

这个判断很有意思，因为它说明：

- Agent 并不是单纯的“模型 + 工具”。
- 它所在的宿主环境也会反过来塑造架构。
- 在 IDE 中运行的 Agent，天然更容易接入编辑上下文、诊断信息、光标位置、文件变更流等高价值信号。

所以，IDE 集成不是纯产品层问题，它会直接影响工具设计、上下文策略、交互循环甚至安全边界。

## 5. 我对三层架构的理解

## 5.1 第一层决定“Agent 像不像一个真正会做事的执行体”

如果第一层太弱，Agent 就只是在做问答增强；如果第一层足够强，它才会表现出真正的任务推进能力。

我理解这一层的本质是：

- 是否有持续推进任务的闭环
- 是否有失败后的修复或回退能力
- 是否有计划、验证、重试、搜索之间的组合机制

这层更像 Agent 的“操作系统内核”。

## 5.2 第二层决定“Agent 能看到什么、能改什么、能安全地做什么”

这一层最贴近工程落地。

很多 Agent 表面上都说自己“能读代码、改代码、跑测试”，但真正差异在于：

- 是直接给 shell，还是给结构化工具
- 是让模型自己找上下文，还是先做受控检索
- patch 是自由文本，还是受限格式
- 执行是否隔离，变更是否可回滚

也就是说，第二层决定的是 Agent 的 **操作面与安全面**。

## 5.3 第三层决定“Agent 能不能在复杂任务里活下来”

短任务里，大家都像；长任务里，资源管理能力会迅速拉开差距。

这层我最关注三个点：

- 状态是否可持续表达，而不是全靠对话历史硬撑
- 上下文是否能压缩和重建
- 是否能根据任务阶段切换不同模型，平衡成本与质量

第三层不像第一层那么显眼，但它往往决定系统上限。

## 6. 论文对实践设计的启发

结合论文结论，我认为设计 Coding Agent 时可以优先把以下问题想清楚。

### 6.1 先设计循环原语组合，再设计统一大脑

比起追求一个包打天下的总循环，更有效的方式是：

- 用主循环负责任务推进
- 用局部循环做测试修复、重试、评估、分支搜索
- 让不同子流程处理不同失败模式

这会比单一控制结构更稳。

### 6.2 工具接口要按“认知负担”设计

工具设计不能只从实现方便出发，还要从模型是否容易选对、是否容易学会稳定使用出发。

一个实用原则是：

- 优先保证工具边界清晰
- 优先保证返回结果可消费
- 再考虑是否要继续拆分工具

### 6.3 把上下文压缩当成一等公民

如果一个 Agent 目标是处理真实工程任务，就应该在早期就回答：

- 何时裁剪上下文
- 裁剪后保留什么结构
- 如何把历史压缩成状态而不是简单丢弃
- 如何在后续轮次恢复关键事实

### 6.4 状态和记忆要分层

从论文的资源管理视角看，至少要区分：

- 当前任务的过程状态
- 项目级长期约束
- 可复用的失败经验与操作流程

如果这些都混在聊天历史里，系统会越来越重，也越来越不稳定。

### 6.5 模型能力和脚手架能力要分开评估

这是研究和工程里都很容易忽视的一点。

如果一个 Agent 表现更好，不一定说明模型更强，也可能是：

- 它的上下文检索更准
- 它的失败恢复循环更强
- 它的工具暴露方式更适合模型
- 它的状态压缩更合理

所以评估 Agent 时，应该尽量把模型因素和脚手架因素拆开看。

## 7. 我认为这篇论文最有价值的地方

我觉得这篇论文最有价值的不是“给出一个标准答案”，而是给出一个 **足够工程化的观察框架**。

它帮助我把 Coding Agent 的设计理解成下面这组问题：

- 任务推进闭环怎么组织
- 工具接口怎么建模
- 上下文如何检索、压缩和恢复
- 状态如何外置与持久化
- 多模型如何协同
- 宿主环境如何反向塑造架构

这比单纯讨论“Agent 有没有规划能力”更接近真正的系统设计。

## 8. 我自己的结论

如果把这篇论文压缩成一句工程判断，那就是：

> Coding Agent 的竞争力，越来越不只是模型本身，而是模型外那套脚手架系统的组合质量。

进一步展开，就是三点：

- Agent 设计正在从“能力标签竞争”转向“架构组合竞争”。
- 长任务表现的关键，在于控制循环、上下文压缩、状态管理和工具接口是否协同。
- 未来很多差异化能力，未必来自更大的模型，而可能来自更好的 scaffold 设计。

## 9. 可直接复用的阅读提纲

后续再看别的 Agent 论文或代码库时，我会优先按这 12 个问题去看：

- 控制循环是什么
- 循环由谁驱动
- 控制流如何实现
- 工具集合如何设计
- patch/edit 如何表达
- 工具如何被发现与选择
- 上下文如何检索
- 执行如何隔离
- 状态如何管理
- 上下文如何压缩
- 是否有多模型路由
- 是否有持久记忆

这个提纲本身就很适合作为阅读和拆解 Coding Agent 的通用模板。
